cheat-enginer for Android · 架構說明

兩支 APK，一個行程

一支獨立安裝的記憶體掃描器，怎麼在沒有 root 的情況下讀寫另一支獨立安裝的遊戲的記憶體。 答案不是繞過權限，而是讓兩支 APK 從一開始就跑在同一個 OS 行程裡 —— 於是「跨行程」這個問題根本不存在。 以下用 SVG + SMIL 動畫說明關聯架構、運作架構、用到的 Android framework，以及它們怎麼連通。

驗證環境 Android 15 / API 35 模擬器 · x86_64 引擎 Rust · ce_engine v0.2.0 UI 純 framework Views · 零 AndroidX / Kotlin / XML
00

為什麼不需要 root

整份架構壓在三句話上，順序不能顛倒：

  1. 讀自己的記憶體只要開 /proc/self/mem —— 不需要任何權限，也沒有 SELinux 規則擋。
  2. 讀別人的記憶體需要 ptrace 或 /proc/<pid>/mem；stock Android 的 SELinux policy 對 untrusted_app 是 neverallow，沒有商量餘地。
  3. 所以掃描器必須就在被掃的那個行程裡。剩下的全部工程，都只是在回答「怎麼進去」。

這個專案有兩種「進去」的方法，共用同一套引擎與同一套 UI，只有視窗掛在哪裡不同。

01

關聯架構：從 Rust 到三支 APK

引擎是一份 Rust crate，同時產出桌面 TUI 執行檔與 Android 用的動態庫。 cargo-ndk 把 cdylib 交叉編譯成 libce_engine.so， 丟進 :overlay 這個 AAR；兩支 App 各自用不同的 Gradle configuration 取用它， 而遊戲完全不取用。

02

運作架構：兩個 package 合併成一個行程

獨立模式的全部魔法只有兩個 manifest 屬性加一把相同的簽章金鑰。 android:sharedUserId 讓兩支 APK 拿到同一個 Linux uid， android:process 給一個全域行程名（不能以 : 開頭， 那是 package 私有的形式，永遠共用不了），ActivityManager 於是把兩者裝進同一個 ProcessRecord。

兩個 ClassLoader 帶來的實際後果

CE package 註冊的 ActivityLifecycleCallbacks 永遠不會收到遊戲的 Activity， 因此也拿不到它的 windowToken —— 嵌入模式那條 TYPE_APPLICATION_PANEL 的路在跨 package 時直接不成立。 而且在共用行程裡，只有建立行程的那個 package 會在 bind 階段安裝自己的 ContentProvider， 後加入的那個是 lazy 的 —— 所以 CE APK 用 tools:node="remove" 拿掉了 OverlayInstallProvider，一切改由 Service 明確驅動。

03

「視窗畫在哪裡」與「誰的記憶體可讀」是兩件互不相干的事，各自可能單獨失敗， 底下的清單也照這個界線分組。先看視窗這一半 —— 三層視窗的 z-order，以及觸控事件實際落在哪一層。

原生介面與記憶體

System.loadLibrary("ce_engine")
JNI（jni crate 0.21）
26 個匯出函式，全部包 catch_unwind —— 任何 unwind 進 JVM 都是立即當掉，所以 Android profile 永遠不可以設 panic = "abort"。
/proc/self/maps
列出可讀寫的 region。無條件排除 /dev/**、[vvar]、[vsyscall]、[vectors] —— 讀這些會掛。
/proc/self/mem
pread / pwrite
用 FileExt::read_at/write_at 操作快取的 fd，&self 即可、沒有 seek race。短讀截斷而非整個失敗。
ByteBuffer.allocateDirect
在 Android 上會拿到 ART 的 non-movable byte[]，所以位址在行程存活期間穩定 —— 這正是遊戲把狀態放這裡的原因。
對照組
普通物件的 instance 欄位
住在 region space，會被 concurrent-copying GC 搬走，位址隨時失效。static 原始型別反而住在 Class 物件、non-moving space，示範不出這件事。

怎麼連通：一次寫入的完整路徑

從手指到遊戲畫面改變，中間只有一條路。上方那條是寫入（使用者驅動）， 下方那條是讀回（Java 每 250 ms 主動 poll）。 關鍵設計是沒有任何 JNI 呼叫從 Rust 執行緒發出 —— 掃描與凍結執行緒只碰 atomics 與 Rust 自己的資料，由 Java 來輪詢， 這樣就整類消滅了 AttachCurrentThread 相關的當機。

實際跑過的一次寫入

# 掃描：u64，把 gold 與 score 一起當成一個值（極為獨特，一輪就收斂）
gold = 15, score = 59
  → 59 × 2^32 + 15 = 253403070479
  → Exact Value / 8 Bytes (u64) / New Scan        → 7 筆
  → 其中 0x732B0088 就是 GameState 的 gold 欄位

# 寫入：一次改掉兩個欄位
  gold = 99999, score = 1000
  → 1000 × 2^32 + 99999 = 4294967395999
  → nativeTableSetValue → write_memory → pwrite(/proc/self/mem)
  → 遊戲 HUD 200 ms 後重繪：gold 99999　score 1000

# 凍結：勾 F，買五把劍（atk 3 → 13，共扣 300 金）
  gold  99999   ← Rust 每 100 ms 寫回，扣款完全無效
  javaGold 99939   ← Java 鏡像沒被寫，漂走了

# 同一個數字、兩個位置 —— ART 搬移式 GC 的教學點自己演出來了

兩種部署模式的唯一分歧

WindowHost 這個介面把「視窗掛在哪裡」隔離成唯一的變異點。 它上面的所有東西 —— session、面板、位址表、掃描流程 —— 兩種模式完全共用。

為什麼權限宣告不能寫在 AAR 裡

SYSTEM_ALERT_WINDOW 與 <service> 只宣告在 :cheatengine 的 manifest。一旦寫進 :overlay， manifest merger 會把權限推進每一支使用這個 AAR 的宿主 debug APK，嵌入模式「零權限」的性質就沒了。 aapt dump badging 已確認 :sample 與 :game 兩支 APK 都沒有任何 uses-permission。

06

邊界與已知限制

  • 這不是通用的作弊器，也做不到。 它只能看見自己所在的那個行程。任意 App 的記憶體在 stock Android 上需要 root，這個專案刻意不往那走。
  • android:sharedUserId 自 API 29 起 deprecated，Play 也擋新 App 使用。對 sideload 的開發工具沒問題、API 35 實測可用，但這是獨立模式唯一可能被平台拿掉的地基。若真的失效，退路是把無 UI 的 agent 內嵌進遊戲、CE 變成 localhost socket 的遠端 UI —— 代價是遊戲不再完全獨立。
  • package 的 uid 在安裝當下就固定了。 事後補 sharedUserId 沒有作用，覆蓋安裝會得到 INSTALL_FAILED_UID_CHANGED。必須兩支都解除安裝再重裝。CE 啟動器會主動比對 uid 並在畫面上講明，因為另一個症狀是「一切正常但掃不到東西」。
  • am force-stop 任一支都會殺掉整個共用行程，掃描結果與凍結執行緒一起沒。重裝任一支 APK 也一樣。位址表存在 CE 的 filesDir，下次啟動會重新載入。
  • ART 的搬移式 GC 是本質限制，不是 bug。 普通 Java 欄位的位址在 GC 之後可能不再是那個值的位址。遊戲用 direct ByteBuffer 當主要示範對象，並保留一個會漂走的 Java 鏡像當對照。
  • 實機測試都在 x86_64 模擬器上。 arm64 的 .so 有編出來、也是 16 KB page 對齊，但沒有在真機跑過 —— /dev/* 排除清單與廠商 SELinux 政策正是真機才會不同的地方。
